# ADR-0030. Фильтры, сортировки, итоги и детализация: сверка с legacy (AC-08)

Статус: **принято**. Дата: 19.10.2026. Требования: TEST-AC-08 («Фильтры, сортировки, выделение, ресайз, drill-down —
повторяют исходные действия и данные; источник итогов не ограничен текущей страницей пагинации»), часть ERP-071.

## Решения

1. **`make visual-filters`** — сверка с legacy (`tests/visual/legacy_compare.py`) с `FILTERS=1`, на копии реальных
   данных. Обе стороны держат одни и те же строки: legacy получает ровно то, что показывает новая версия. В первой теме
   для каждой перенесённой вкладки, где есть фильтры (`tests/visual/filters.py`), сверка выполняет действия:
   - **фильтры и сортировки** — все, что реестр отмечает как перенесённые (ADR-0029). Сверка находит их сама, по id и
     строкам эталона; список вручную не ведётся;
   - **список** — каждый вариант по его месту в списке; при длинном списке — первые и последние шесть. Подписи
     вариантов сравниваются;
   - **поиск** — пробы «а», «о», «ТОО», «1», «zzqq»;
   - **число** — 1000 и 100000;
   - **дата** — начало года и конец июня;
   - **флажок** — переключение;
   - **сортируемый столбец** — два щелчка.
2. **Что сравнивается.** Таблицы вкладки (тело и итоговая строка), счётчики, KPI, а где вместо таблиц доски и карточки
   — сами доски. Сравнение идёт по строкам, в их порядке. Из браузера выходят только короткие хеши строк и ячеек, а
   при расхождении — какая часть и какие столбцы. Данные не выводятся.
3. **Каждый случай начинается с исходного состояния.** Значения возвращаются. После сортировок новая версия щёлкает
   исходный столбец, пока таблица не станет прежней; legacy повторяет те же щелчки, потому что стрелку в заголовке он
   обновляет не всегда. Где отмена фильтра в legacy заново запускает его логику с записанным отличием, состояние
   legacy возвращается явно: период досок заказов (п. 51).
4. **Записанные отличия различаются, а не прячутся.** Расхождение, которое объясняет пункт ADR-0002, выводится
   с номером пункта:
   - по значению фильтра — `KNOWN`;
   - по столбцу таблицы — `KNOWN_COLUMNS`;
   - по виду строки legacy, который приводится к виду новой версии, — `LEGACY_RENDERINGS`.

   Строки, которые различаются ещё до любого фильтра, из сравнения исключаются: это записанные отличия вида. Код
   возврата ненулевой только при незаписанном расхождении.
5. **Где сверка честно сравнить не может, она так и говорит.** Месяц дашборда: сверка даёт legacy расшифровку расходов
   только за текущий месяц. Неперенесённый блок «Расчёт ЗП продавцов» не читается.
6. **Детализация (drill-down).** Каждая строка ДДС, которая открывает детализацию, открывается на обеих сторонах.
   Сравниваются заголовок, KPI, таблица и итог окна, а также пробы его поиска.

## Найдено

- **«Касса», фильтр категорий** (новое отличие, ADR-0002, п. 90). У операций без категории в списке есть пустой
  вариант. Legacy при его выборе показывает все операции — пустое значение он заменяет на «Все категории». Новая
  версия показывает операции без категории.
- **«Реализация», строка без номера заказа** (новое отличие, п. 91). В столбце «Заказ» legacy пишет «null».
- **Подтверждены записанные отличия:** пп. 11, 44, 48, 50, 51, 52, 75 (уточнён: выборка без цен), 81.
- **Ошибки самой сверки, исправлены:**
  - legacy подменялся постоянный период «текущий месяц» у закупок финансов, из-за чего «Квартал», «Год» и
    «Произвольный» сравнивались неверно. Теперь legacy считает свои периоды в местных датах;
  - лиды: «Все статусы», «Выиграли» и «Проиграли» заставляют legacy загрузить лиды заново, вместе с закрытыми. Теперь
    на этот запрос отвечают те же лиды, что у новой версии;
  - стрелка сортировки в заголовке legacy принималась за итог;
  - рабочий лист салонов: ячейка с кавычкой (записанный п. 75) больше не считается расхождением.

## Не сделано

- **Выделение строк и ресайз столбцов** есть только в неперенесённых частях: рабочий лист производства, сверка ЭСФ —
  по мере переноса.
- **Детализация акта сверки** (`openRecDrillTx`) загружает платежи прямо из базы legacy, а в сверке база закрыта.
  Сервер, который отдаёт эти платежи, проверяет
  `DealerTest::test_reconcile_tab_loads_orders_and_payments_of_a_visible_order_only`: только приходы, только видимого
  заказа.
- **Месяцы дашборда** — по причине из п. 5.
- **CI.** Сверка не запускается в CI: нужен Playwright на раннере (решение о зависимостях).
