# ADR-0025. Надёжность: большие реестры, каналы, одновременная правка, ошибки

Статус: **принято**. Дата: 16.10.2026. Требования: ERP-072, AC-11, AC-72, AC-73, AC-74 (ТЗ OPS-01).

Проверено на перенесённых разделах. Разделы, которые ещё не перенесены (сотрудники и зарплата, проведение денег, склада и
производства, выгрузки), проверяются так же, когда появятся.

## 1. Большие реестры (AC-74)

1. **Как было в legacy.** Legacy читал часть таблиц одним запросом без постраничной загрузки:
   - Supabase отдаёт не больше 1000 строк — поставщики, авансовые отчёты, статьи расходов, синонимы материалов, проекты;
   - явный `limit=5000` — реализации (D-16), расчёты, файлы и сообщения проектов.

   Здесь ни один список страницы не ограничен. Намеренно ограничены только 8 критичных остатков на дашборде и 20
   последних ЭСФ в карточке поставщика — как в legacy. ADR-0002, п. 83.
2. **Тест** `Tests\Feature\Reliability\LargeRegistriesTest`. В каждом реестре и в каждой вкладке, которая загружается при
   открытии, 6001 синтетическая строка: DATA-01 п. 12 называет пределы 5 000 и 6 000, а 6001 = 6 × 1000 + 1 ловит и
   потерю последней тысячи. Для реестров, которые legacy обрезал (реализации, поставщики, операции счёта), границы
   4999/5000/5001 и 5999/6000/6001 проходятся построчно.
   - Всё на месте: каталог, покупатели, заказы дилеров, поставщики, склад, синонимы и поставщики склада, статьи расходов,
     заявки, ЭСФ, закупки в финансах, заказы, реализации, отчёт и доски заказов, позиции производства, лиды, задачи,
     проекты, клиенты салонов, операции, авансы, рабочий лист салонов, сверка с банком, операции в финансах, касса
     салона, отчёт салонов, сверка дилера.
   - Суммы, которые считает сервер, берут все строки: стоимость склада, долг поставщикам, выручка и приход месяца, долг
     по авансам.
   - Каждый ответ должен прийти быстрее 5 с. Страницы отвечают за десятые доли секунды.
3. **Найдено и исправлено:**
   - Форма поставщика собирала статьи расходов, заново просматривая весь список для каждой группы. При 5001 статье
     `/suppliers` отвечал 36 с, теперь статьи группируются один раз.
   - На таблице без статистики планировщика (сразу после массовой загрузки) запрос сверки дилера шёл 7 с: соединение
     5001 × 5001 вложенным циклом. После `ANALYZE` — 0,1 с. Поэтому после массовой загрузки выполняется `ANALYZE`:
     - шаг `analyze` в `make migration-rehearsal` (порядок дня переноса);
     - `make db-restore-check`;
     - тест.
4. **Реальные данные** (копия legacy, директор). Каждая страница и вкладка отдаёт ровно столько строк, сколько их в
   БД, в том числе больше 5000. Время ответа сервера:

   | Страница (вкладка) | Строк | Время, с | Ответ |
   |---|---:|---:|---:|
   | Склад — материалы | 6299 | 0,95 | 1,9 МБ |
   | Деньги — операции | 6341 | 0,83 | 3,2 МБ |
   | Финансы — операции | 6341 | 0,60 | 2,1 МБ |
   | CRM — лиды | 4964 | 0,97 | 2,0 МБ |
   | Производство — позиции | 4204 | 0,56 | 1,0 МБ |
   | Сверка с банком | 3763 | 0,42 | 2,9 МБ |
   | Заказы | 3146 | 0,54 | 1,4 МБ |
   | Рабочий лист салонов | 3111 | 0,62 | 1,7 МБ |

   Остальные — до 0,6 с. Самый большой ответ — 3,2 МБ. Для медленной сети это заметно; серверная разбивка на страницы
   допустима (ТЗ OPS-01), если итоги и выгрузка остаются полными. Решение — по замерам у заказчика (D-16).

## 2. Чужой канал (AC-11)

`Tests\Feature\Reliability\ChannelIsolationTest`:

1. У каждого канала (офис, два салона, два дилера) своя метка в текстах:
   - покупатели, лиды, сообщения и задачи;
   - заказы, позиции, прогресс производства, реализации;
   - оплаты, касса салона, рабочий лист;
   - проекты, сообщения проектов и их файлы.
2. Каждая учётная запись салона, начальника салонов и дилера открывает все страницы своей роли и все вкладки, которые
   загружаются при открытии. Чужой метки нет ни в одном ответе, своя есть (иначе проверка ничего бы не доказывала).
3. По id чужие записи не выдаются: сообщения лида, файл проекта, оплаты заказа. Свой файл выдаётся.
4. Отдельный тест следит, чтобы каждая новая вкладка с загрузкой при открытии попала в проверку.
5. Изменение чужих записей по id отклоняется — это проверяют тесты модулей (лиды, покупатели, задачи, проекты, заказы).
6. Проверка чувствительна: без фильтра канала у лидов CRM тест падает («salon_armada got records of office»).

## 3. Одновременная правка (AC-73)

1. Правка записи передаёт версию, которую видел пользователь. Сервис блокирует строку (`SELECT … FOR UPDATE`) и только
   потом сравнивает версию. Из двух одновременных сохранений второе ждёт первое и получает «изменён другим
   пользователем»; молча оно ничего не перезаписывает.
2. Так устроены все 12 проверок версии:
   - покупатели, дилеры, поставщики, каталог, склад;
   - заявки, статьи расходов, лиды, задачи, заказы;
   - проекты (шапка и удаление).
3. Ячейки рабочего листа салонов сохраняются по одной под блокировкой строки — последовательно, как в legacy; каждая
   правка в журнале аудита.
4. `Tests\Feature\Reliability\ConcurrencyTest`:
   - настоящая гонка: вторая сессия держит строку и сохраняет своё; сохранение теста ждёт её больше секунды, получает
     отказ, чужое изменение на месте;
   - тест-страж: каждая проверка версии в сервисах идёт после блокировки строки.

   Без блокировки оба теста падают: изменение теряется.

## 4. Ошибки, медленная сеть, два нажатия (AC-72)

1. **Ошибки ответа.** Ошибки проверки остаются у своих форм. Любой другой отказ сервера и обрыв связи сообщаются
   окном, как legacy сообщал свои ошибки (`alert`):
   - причина и код (ошибка сервера, нет доступа, не найдено, сессия истекла, слишком много попыток);
   - «Изменения не сохранены — введённое осталось на экране, действие можно повторить».

   Раньше Inertia показывал английскую страницу ошибки, а при обрыве связи не говорил ничего: в консоли оставалась
   необработанная ошибка. Сообщения об успехе приходят только с ответом сервера. ADR-0002, п. 84.
2. **Два нажатия.** Кнопки сохранения недоступны, пока идёт запрос. Повтор правки с версией отклоняется, повтор
   удаления сообщает «не найдено». Нашлось одно создание без защиты — «+ Добавить строку» рабочего листа салонов
   (двойной клик давал 3 запроса); теперь кнопка недоступна на время запроса (ADR-0002, п. 85).
3. **Проверка в браузере** — `make reliability-check` (`tests/e2e/reliability_check.py`). Каждый изменяющий запрос
   перехватывается и до сервера не доходит, данные не меняются. Сценарии:
   - сохранение товара при ответе 500, при обрыве связи и при истёкшей сессии (419): сообщение с причиной, форма
     открыта с введённым, кнопку можно нажать снова, успеха нет;
   - медленная сеть: кнопка недоступна, двойной клик и Enter дают один запрос;
   - двойной клик «+ Добавить строку» — один запрос;
   - ни одной необработанной ошибки в странице.

   17/17 проверок. Без исправлений — 11/17: нет сообщений, 3 запроса на одну строку, необработанная ошибка.

## Не сделано

- Выгрузки (Excel) — с ERP-067: полнота выгрузок проверяется тогда же.
- Проведение денег, склада и производства, зарплата — с их разделами: гонки при проведении (H-22, H-23) и остатки.
- Разбивка больших реестров на страницы — по замерам у заказчика (D-16).
