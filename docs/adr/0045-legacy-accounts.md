# ADR-0045. Учётные записи — как в legacy (D-13)

Статус: **принято**. Дата: 23.10.2026. Решение заказчика 23.10.2026 по D-13:
1. пока использовать пользователей, которые есть в базе;
2. вариант А — новые пароли всем при запуске;
3. матрица ролей — как в legacy.

Требования: ERP-010, ERP-011, ERP-053.

## Контекст

В legacy вход устроен так:
- 15 встроенных учётных записей (`var _USERS`): логин — ключ роли, у каждой имя, инициалы, цвет, подпись роли и разделы;
- таблица `app_users` накладывается поверх (`dbUsersApply`): имя, подпись, инициалы, цвет, разделы, блокировка. Директора
  нельзя заблокировать и лишить разделов его шаблона;
- в снимке 22.10 в `app_users` одна запись. Она меняет разделы одной встроенной роли, «Гл. бухгалтер»: добавляет
  «Производство», «Склад», «Закупки», «Поставщиков», CRM, «Кассу салона», AI и техкарты, убирает «Продажи».

До решения у нас была временная матрица только из шаблонов (ADR-0001), без этой записи.

## Решения

1. **Учётные записи** — `legacy:import app_users`, первым шагом переноса:
   - на каждую встроенную роль — учётная запись с логином-ключом роли и именем и инициалами из legacy (читаются из
     принятого эталона, как счета в ADR-0015);
   - записи `app_users` накладываются как в legacy: имя, подпись роли, инициалы, цвет, разделы, блокировка (директор
     всегда активен);
   - запись с логином, которого нет среди встроенных ролей, отклоняется: новой учётной записи нужна роль. Сейчас таких
     нет;
   - пароли и PIN legacy не читаются. Новая учётная запись получает случайный пароль, которого никто не знает.
     У существующей пароль не меняется.

   Каждая запись после сохранения перечитывается и сравнивается. Контрольные итоги: число записей, активных и с
   разделами.
2. **Права:**
   - разделы учётной записи, если заданы, заменяют разделы её роли;
   - у директора они добавляются к разделам шаблона, как в legacy;
   - неперенесённые страницы (техкарты) в меню и доступе не участвуют, как и раньше;
   - подпись роли, инициалы и цвет в боковой панели — учётной записи, иначе роли.

   Все проверки страниц и действий по-прежнему идут через `Erp::canAccess`, поэтому новые разделы роли открываются вместе
   со всеми проверками канала.
3. **Пароли при запуске (ответ 2, вариант А)** — `php artisan users:issue-passwords --out=<файл>`:
   - каждая активная учётная запись (или названные `--login`) получает новый случайный пароль из 14 знаков, без похожих
     символов;
   - логины и пароли записываются один раз в файл, который читает только владелец (0600). Существующий файл не
     перезаписывается;
   - в консоль, журнал и аудит пароли не попадают; в базе — только хеши;
   - старые сессии завершаются, в журнале аудита — список логинов.

   Шаг добавлен в план переключения (`docs/OPERATIONS.md`, раздел 11).
4. **Не сделано:**
   - вход по PIN и «Мой кабинет» — с ERP-058; PIN выдаются заново (вопрос № 42);
   - вкладка «Пользователи» в «Сотрудниках» (создание и правка учётных записей) остаётся сообщением. Создание новой
     учётной записи требует решения о роли.

## Проверено (23.10.2026)

- `AppUserImportTest`:
  - учётные записи всех ролей;
  - наложение записи: разделы, подпись, инициалы, цвет;
  - директор не блокируется и сохраняет разделы шаблона;
  - пустой список разделов оставляет разделы роли, блокировка работает;
  - пароль существующей записи не меняется, пароль legacy не берётся;
  - повтор без изменений, неизвестный логин отклоняется целиком.
- `IssuePasswordsTest`:
  - новые пароли только активным учётным записям;
  - файл с правами 0600, в выводе паролей нет;
  - старые пароли перестают подходить, в аудите паролей нет;
  - существующий файл не перезаписывается.
- Dev-БД: перенос записей, контрольные итоги — совпадает.
