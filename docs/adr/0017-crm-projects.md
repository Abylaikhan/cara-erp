# ADR-0017. CRM «Проекты» (M10, ERP-079)

Статус: **принято**. Дата: 15.10.2026. Источник legacy (`c917d37`): разметка `orders-projects` L4265–4281; `PRJ_STATUSES`,
`loadProjects`, `prjOpenTab`, `prjFillExecFilter`, `renderProjects` L31099–31252; окно проекта `prjOpenNew`/`prjCreate`/
`prjRenderCard`/`prjCalcHtml`/`prjSaveHead`/`prjClientDecide`/`prjToOrder`/`prjDeleteProject`/`prjCalc*`/`prjUpload*`/
`prjDeleteFile`/`prjAddComment` L31254–31720; `prjApplyRole` L31725.

## Решения

1. **Данные.** Таблицы `projects`, `project_calcs`, `project_files`, `project_comments` повторяют поля, которые пишет
   legacy (сами таблицы в снимке пустые, их схема известна только из кода). Номер — `ПР-` и id из 4 цифр. Исполнители — логины
   сотрудников (как `projects.responsible`), имена хранятся рядом для истории. Импорт: `legacy:import projects` (проекты,
   версии расчёта, сообщения) с построчной сверкой; пустой набор — нормальное состояние (в legacy 0 проектов). Файлы legacy
   лежат в хранилище Supabase, которое копия только чтением пока не читает, — при появлении файлов импорт откажет целиком.
2. **Права проверяет сервер** (`ProjectPolicy`, `ProjectService`).
   - Заказчик — учётная запись салона или дилера (legacy `prjIsClient`). Он видит проекты своего канала, создаёт запрос
     только на свой канал, правит название, описание и срок, пока запрос не взят в расчёт, принимает или отклоняет
     отправленный расчёт, добавляет файлы только в колонку «От заказчика» и удаляет только свои файлы.
   - Заказчику не отдаются себестоимость, неотправленные версии расчёта, внутренние файлы и сообщения. Legacy загружал их в
     браузер и только не показывал.
   - Сотрудники считают, отправляют, назначают исполнителей (только пользователей без канала), меняют статус и номер заказа.
     Номер заказа переводит проект в «Стал заказом», если он не закрывается.
   - Удаляет проект только директор.
   - Проекты выбираются через `ChannelScope`: начальник салонов видит проекты салонов (в legacy — все, ADR-0002, п. 61).
3. **Расчёт.** Строки с названием или ценой сохраняются; сумма qty × цена считается сервером точно (`numeric`, bcmath);
   на экране — целые тенге, как в legacy. Неотправленная версия обновляется, отправленная не меняется — сохранение создаёт
   следующую версию, как в legacy. Автор расчёта становится исполнителем, «Запрос» переходит в «В расчёте». Отправка
   сохраняет расчёт, ставит «Отправлен заказчику» и пишет сообщение в обсуждение одной транзакцией.
4. **Файлы** хранятся на сервере (`storage/app/private/projects`), до 25 МБ, тип определяется по содержимому. Открываются
   только пользователю, который видит проект (внутренние — только сотрудникам). Картинки (JPEG, PNG, GIF, WebP, BMP)
   показываются в карточке, остальное скачивается и никогда не открывается как страница. Фото больше 1,5 МБ сжимаются в
   браузере перед загрузкой, как в legacy.
5. **Версия записи.** Поля шапки (название, описание, срок, статус, номер заказа) защищены `lock_version`: устаревшая форма
   получает сообщение. Статус и сумму меняют также расчёт, отправка и решение заказчика — они тоже повышают версию. Исполнители,
   файлы и сообщения версию не меняют, но обновляют «Обновлён».
6. **Удаление** проекта — деактивация: проект, расчёты, файлы и сообщения остаются для истории (legacy удалял всё).
7. **Заказ из расчёта** (`prjToOrder`/`prjCreateOrder`) — сообщение: создание заказа ждёт ERP-029 (решения D-02, D-12).
8. Журнал аудита: создание, шапка, исполнители, версии расчёта, отправка, решение заказчика, файлы, удаление.

## Ограничения

- `make db-backup` копирует базу, но не файлы проектов: резервное копирование `storage/app/private` — отдельной задачей
  к запуску (ERP-074).

## Проверка

`tests/Feature/Crm/ProjectTest.php` (9 тестов: создание и номер, каналы и скрытые данные заказчика, версии и точные суммы,
отправка и решение, шапка и версия записи, исполнители, файлы и скачивание, удаление, счётчик),
`tests/Feature/Legacy/ProjectImportTest.php`; `make visual-compare`: список и окно нового проекта 0,00–0,02 %; карточка с
теми же данными в legacy — 0,07 %; браузерная проверка: менеджер создаёт проект дилера, считает, применяет наценку,
пишет; директор отправляет расчёт, загружает фото, пишет внутреннее сообщение; дилер видит только «Проекты», расчёт без
себестоимости, без внутреннего сообщения, принимает расчёт. Данные проверки удалены.
