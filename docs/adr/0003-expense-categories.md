# ADR-0003. Статьи расходов (M14): хранение, удаление и объединение

Статус: **принято**. Дата: 14.10.2026. Источник legacy: page-expense_cats L6786–6875, функции L11068–11257. Находка QA-062.

## Решения

1. **Стабильные ID.** Строки получают `id`; родитель — по `parent_id`. Код (`^[a-z0-9_]+$`) уникален навсегда, в том числе
   после удаления: на него ссылаются исторические операции legacy. Проверка формата и «не свой родитель» — также в БД.
2. **Два уровня, как в legacy.** Категория остаётся категорией, статья — статьёй; статья требует активной категории
   первого уровня (legacy при пустом списке молча создавал категорию).
3. **Удаление = деактивация** (`active = false`), как в legacy, но список после перезагрузки показывает только активные:
   legacy загружает `select=*` без фильтра, и «удалённая» статья возвращалась после reload. Ссылки операций на
   деактивированную статью сохраняются — классификация расходов не теряется.
4. **Объединение** — одна транзакция с блокировкой обеих строк: все зарегистрированные ссылки
   (`config/erp.php → expense_category_references`) переводятся на целевую статью, источник деактивируется с
   `merged_into_id`, в `expense_category_merges` пишется отчёт «до/после» по каждой таблице (AC-58). При сбое любого шага
   ничего не меняется. Legacy менял только `money_tx.category` отдельным запросом (QA-062). Модули денег, поставщиков,
   авансов и ЭСФ добавят свои ссылки в реестр при переносе.
5. **Одновременная правка** выявляется по `lock_version`: второй пользователь получает понятное сообщение, а не затирает чужие
   изменения. Повторное объединение (двойной клик) отклоняется без изменений.
6. **Порядок сортировки 0** сохраняется как 0 (legacy `parseInt(x)||50` превращал 0 в 50). Пустое значение — 50.
7. **Журнал аудита** (`audit_events`): создание, изменение (было/стало), деактивация, объединение — автор и время.

Тексты, кнопки, подтверждения (`confirm`) и сообщения повторяют legacy.

## Дополнение 16.10.2026: ссылки по коду и проверка на реальных данных

- После переноса «Денег» и авансовых отчётов нашлись ссылки на статьи **по коду**, а не по id:
  - строки авансовых отчётов (`lines[].subcategory`, группа — `lines[].category`) — 363 строки;
  - группа статьи у денежной операции (`money_transactions.category`).
- Объединение теперь переписывает и их в той же транзакции: код статьи в строках авансов, а при объединении статей из разных
  групп — код группы в этих строках и у операций статьи. Отчёт «до/после» включает строки авансов. Legacy менял только
  `money_tx.category`.
- Проверка на копии реальных данных (транзакция с откатом): объединение самой используемой статьи со статьёй другой группы —
  453 операции, строка аванса и поставщик перешли, группы переписаны, суммы строк не изменились; после отката всё как было.
  Тест — `ExpenseCategoryTest::test_merge_rewrites_the_article_codes_of_advance_lines_and_the_group_of_money_operations`.
- Фильтры (поиск, категория, «Только постоянные») сверены с legacy: пять сочетаний на тех же данных дают ту же таблицу.
