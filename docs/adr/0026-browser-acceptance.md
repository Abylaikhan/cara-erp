# ADR-0026. Сквозные сценарии приёмки в браузере (make e2e)

Статус: **принято**. Дата: 16.10.2026. Требования: TEST-AC-18, TEST-AC-19, TEST-AC-20 (ACCEPTANCE AC-18…20).

## Решения

1. **Отдельное окружение.** dev-БД хранит копию реальных данных legacy, поэтому сценарии, которые создают и меняют
   записи, работают только с временной БД. `make e2e` (`scripts/e2e.sh`):
   1. создаёт пустую БД `promtech_e2e_<время>`, выполняет миграции и синтетический сид;
   2. запускает отдельный экземпляр приложения: встроенный сервер PHP с роутером Laravel, `127.0.0.1:E2E_PORT`;
   3. выполняет `tests/e2e/acceptance_*.py` (Playwright и Chrome на хосте, как `make visual-compare`);
   4. удаляет БД. `KEEP=1` её оставляет.
2. **Две защиты dev-БД:**
   - до сценариев экземпляр должен показать метку своего окружения (имя приложения с именем временной БД). Иначе
     ничего не запускается;
   - отпечаток dev-БД (`scripts/sql/db-fingerprint.sql`, без сессий, кеша и очереди) снимается до и после прогона.
     Любое изменение — ошибка «THE DEV DATABASE CHANGED».
3. **Не `php artisan serve`.** Эта команда намеренно очищает окружение дочернего процесса и перечитывает `.env`, поэтому
   `DB_DATABASE` временной БД до приложения не доходит.

## Инцидент 16.10.2026

Первые три прогона шли через `php artisan serve`, и по причине из п. 3 сценарии записали синтетические записи в
dev-БД:
- 12 лидов, 12 задач, 2 записи коммуникаций, 3 покупателя;
- их записи аудита и сессии безголового браузера.

Реальные записи не изменялись. Устранено:
- перед очисткой сделана резервная копия dev-БД;
- в одной транзакции удалены только эти записи — по синтетическим названиям «Е2Е …», времени создания и id;
- `legacy:control-totals` снова показал 22 из 22 модулей «совпадает» с legacy.

Окружение переделано (пп. 1–3). Защита по метке сработала в деле: при запуске сервера не из того каталога прогон
отказался начинаться. Сравнение отпечатков dev-БД выполняется в каждом прогоне; во всех следующих dev-БД не изменилась.

## Сценарии CRM — `tests/e2e/acceptance_crm.py`, 23/23

1. **AC-18 «Лид → стадии → выигрыш»:**
   - новый лид в списке, счётчик вкладки +1;
   - «Контакт» в списке — «Квалификация» в воронке, сразу и после перезагрузки;
   - «✅ Выиграли» в воронке предлагает заказ; выигранный уходит из воронки и в списке стоит «Выиграли»;
   - двойное «→ Клиент»: оба запроса дошли до сервера, покупатель один — второй отклонён.

   Заказ из лида появится с заказами (ERP-029, D-02, D-12).
2. **AC-19 «Отказ, сегмент, теги, коммуникация, фильтры».** После перезагрузки сохраняются:
   - отказ с причиной («Отказ: …» в комментарии, как legacy);
   - сегмент и тег на карточке, фильтры по сегменту и тегу;
   - запись коммуникации в истории;
   - поиск в списке.
3. **AC-20 «Задачи».** Часы браузера стоят на сегодняшнем полудне по Алматы, а «сегодня» — бизнес-дата сервера.
   Сценарий:
   - четыре задачи: вчера, сегодня в 11:00 и 18:00, завтра по лиду;
   - счётчики: по лидам 1, общих 3, открытых 4; просрочено 2;
   - выполнить: просрочено 1, открытых 3; вернуть: снова 2 и 4;
   - удалить: общих 2, открытых 3, просрочено 1.

   Каждый шаг проверен и после перезагрузки. Необработанных ошибок в странице нет.

## Не сделано

- В CI сценарии не запускаются: нужен Playwright на раннере — отдельное решение о зависимостях CI.
- AC-18 «→ заказ» — после переноса заказов.
- Сценарии других разделов — по мере переноса (AC-16, AC-17, AC-21 и далее).
