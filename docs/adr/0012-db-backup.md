# ADR-0012. Резервная копия БД и проверка восстановления

Статус: **принято**. Дата: 14.10.2026. Требования: ТЗ harness ENV-03 (`make db-backup`, `make db-restore-check`), H-24.

## Решения

1. **Копия** (`make db-backup`) — `pg_dump` в custom-формате из контейнера `db`, без владельцев и прав. Рядом манифест:
   коммит приложения, ветка и признак незакоммиченных изменений, версия PostgreSQL, размер и SHA-256 дампа, отпечаток БД.
   - Папка — `.local-audit/backups/<время UTC>-<коммит>/`, вне Git, права только у владельца (0700/0600): в dev-БД лежит
     копия реальных данных legacy.
   - Отпечаток снимается до и после дампа. Если БД менялась во время копирования, копия делается заново (до трёх раз).
2. **Отпечаток** (`scripts/sql/db-fingerprint.sql`):
   - по каждой таблице — число строк и MD5 строк без учёта порядка;
   - по каждой последовательности — последнее значение, чтобы новые записи продолжили нумерацию;
   - по схеме — столбцы, типы, обязательность, значения по умолчанию, правила сортировки, ограничения и индексы.
   - Настройки сессии (пояс, формат дат и чисел) фиксированы, иначе текст строк зависел бы от сервера.
   - Выражение CHECK после восстановления PostgreSQL печатает с другой, равнозначной расстановкой приведений типов.
     Поэтому CHECK сравнивается по таблице, имени и столбцам, остальные ограничения — по полному определению.
3. **Проверка восстановления** (`make db-restore-check`, по умолчанию — последняя копия) работает так:
   - сверяет SHA-256 дампа;
   - поднимает временный контейнер того же образа PostgreSQL без сети, с данными в памяти;
   - восстанавливает копию и сравнивает отпечаток с манифестом.
   dev-БД не затрагивается; результат — `restore-check.json` рядом с копией, при любом расхождении — ненулевой код.
4. **Где проверяется:**
   - каждый аудит выполняет шаг `backup` (`TGT-BACKUP`, обязательный) на своей синтетической БД после миграций;
   - самопроверка H-24 делает то же на временной БД сервиса `db` и убеждается, что подменённый отпечаток и
     повреждённый дамп отклоняются.
   `make check` копий не делает: dev-БД с реальными данными копируется только по явной команде.

## Часть 2. Файлы и приложение на копии (ERP-074, AC-77, 16.10.2026)

Критерий: «Изолированное восстановление сохраняет связи, суммы и доступ; приложение поднимается».

1. **Файлы в копии.** `make db-backup` копирует и загруженные файлы: каталог `storage/app` (диск `local` — `private/`,
   там файлы проектов CRM; диск `public` — `public/`). Файлы `.gitignore` данными не считаются.
   - Копия: `files.tar` с отсортированными файлами, без владельца, права 0600/0700, и список `files.tsv` (путь, размер,
     SHA-256). `--files DIR` задаёт другой каталог.
   - Ссылки и в каталоге, и вне его отклоняются, копия не делается.
   - Перед копированием проверяется, что у каждой строки `project_files` есть файл того же размера. Файлы без строки
     считаются (сироты). Если файла уже не было, копия делается с предупреждением, а пути записываются только в
     манифест.
   - Состояние файлов (путь, размер, время) снимается до и после копии вместе с отпечатком БД. Если что-то изменилось,
     копия делается заново.
2. **Что видит приложение** (`php artisan app:view-digest`). При копии каждый активный пользователь открывает каждую
   страницу и каждый файл проекта, который ему выдаёт CRM. Гость открывает вход и закрытую страницу.
   - Записываются HTTP-статус и SHA-256: props страницы, адрес перенаправления или байты файла. Самих данных нет.
     Это и есть проверка сумм, связей и доступа (разрешённая страница — 200, запрещённая — 403).
   - Часы заморожены на моменте копии, поэтому «сегодня» и текущий месяц те же при проверке в любой день.
   - Сессии и кеш хранятся в памяти: при чтении в БД ничего не пишется, отпечаток до и после копии не меняется.
   - Списки сравниваются как наборы. Порядок строк запроса без полного `ORDER BY` выбирает планировщик, и после
     восстановления он может стать другим. Первый прогон нашёл такой запрос: `dealerOrders` у «Покупателей» отличался
     только порядком строк. Запрос получил явный порядок.
   - Файл `views.tsv` лежит рядом с копией (0600), число ответов — в манифесте (`promtech.db-backup/2`).
3. **Проверка восстановления** (`make db-restore-check`):
   1. SHA-256 дампа и архива сверяются до восстановления.
   2. БД восстанавливается во временный контейнер PostgreSQL. Для проверки приложения он подключается к сети проекта,
      без опубликованного порта; иначе запускается без сети. Отпечаток сравнивается, затем выполняется `ANALYZE`
      (`pg_restore` статистику не собирает).
   3. Файлы распаковываются во временный каталог только для владельца. Пути вне каталога, ссылки и особые файлы
      отклоняются. Каждый файл сверяется со списком, лишних и недостающих быть не должно. Ссылки `project_files`
      восстановленной БД должны совпасть с состоянием при копии.
   4. Разовый контейнер образа приложения видит только восстановленную БД и файлы (только чтение) и сравнивает ответы
      с `views.tsv`. Сначала он проверяет, что миграции копии и кода совпадают.
   5. Если коммит копии не совпадает с текущим кодом, проверка приложения пропускается с пояснением: ответы зависят от
      кода.
   - В консоль выводятся только количества, id пользователей и адреса. Пути файлов (имена могут быть персональными)
     попадают только в `restore-check.json` (0600).
   - Временный контейнер и каталог с файлами удаляются в любом случае.
4. **Где проверяется:**
   - `TGT-BACKUP` в каждом аудите: синтетическая БД аудита, её пользователи и страницы;
   - самопроверка H-24 (`tests/Harness/test_backup.py`):
     - копия с файлами и с отсутствующим файлом проекта;
     - подменённый файл в архиве с «исправленным» SHA-256;
     - путь `../` в архиве;
     - сквозной тест: БД со схемой приложения, синтетические пользователи, проект и файл; приложение на копии отвечает
       так же, подменённый файл — другой ответ;
   - PHPUnit `Tests\Feature\Ops\ViewDigestTest`: изменённая сумма, пропавший файл, изменённая роль, замороженные
     часы, отсутствие записи, чужие миграции.
5. **Результат на dev-БД** (копия реальных данных legacy, код этих изменений):
   - копия: 45 таблиц, 35 последовательностей, файлов 0 (в legacy нет файлов проектов), 386 ответов — 17 пользователей
     с гостем;
   - проверка: схема, все таблицы и последовательности совпадают, 386 ответов приложения на копии совпали
     (200 — 113, 302 — 17, 403 — 256);
   - около 30 с на копию и 35 с на проверку.

### Восстановление (порядок)

1. Проверить копию: `make db-restore-check BACKUP=<каталог>` — PASS.
2. Код: коммит `app.commit` из `manifest.json`.
   - `.env` в копии нет: пароли БД и `APP_KEY` хранятся отдельно.
   - Шифрованных данных в БД нет. Новый `APP_KEY` только завершает сессии, пользователи входят заново со своими
     паролями: хеши паролей в БД.
3. БД — в новую пустую базу; рабочая не перезаписывается, пока новая не проверена:
   - `createdb`;
   - `pg_restore --no-owner --no-privileges --exit-on-error -d <новая> db.dump`;
   - `ANALYZE`;
   - `DB_DATABASE=<новая>` в `.env`.
4. Файлы: `python3 scripts/backup_files.py verify files.tar files.tsv <пустой каталог>`, затем каталог становится
   `storage/app`.
5. `php artisan migrate --force`: нужен, только если код новее копии. Затем `make doctor` и вход.

## Не сделано

- Хранение копий вне рабочей машины, расписание копирования и восстановление в production — решение по инфраструктуре
  заказчика (D-01). Production-публикация — отдельный этап (ТЗ OPS-01).
- Восстановление по шагам выше на чистой машине другим исполнителем — с инструкцией передачи (ERP-077).
