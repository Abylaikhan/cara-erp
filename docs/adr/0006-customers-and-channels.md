# ADR-0006. Покупатели (M08, вкладка «Контрагенты») и каналы продаж (ERP-023)

Статус: **принято**. Дата: 14.10.2026. Источник legacy: page-customers L3640–3826, personModal L8417, `loadCustomersFromDB`
L954, `renderPersons`/`openPersonModal`/`savePerson` L18856–18984, `showCustTab` L19061, `SALES_CHANNELS`/`CH_GROUPS` L15213,
`getChannelFilter`/`channelMatches` L15269.

## Решения

1. **Каналы — справочник `sales_channels`.** Восемь каналов legacy с их кодами: офис, два салона, пять дилеров; группы
   «Прямые продажи»/«Салоны»/«Дилеры»; регионы дилеров из `dealersData`. Канал пользователя и канал покупателя ссылаются на
   справочник (внешний ключ): неизвестный канал записать нельзя.
2. **Область данных по каналу проверяет сервер** (`App\Support\ChannelScope` — `getChannelFilter`/`channelMatches` legacy).
   Учётная запись салона или дилера видит только свой канал. Начальник салонов (роль без канала) видит оба салона: legacy
   перечисляет их явно, здесь они берутся из группы «Салоны» справочника. Офисные роли видят все каналы. Ограничение действует
   на выборку и на правку: покупатель чужого канала для правки «не найден» (AC-11). Страницу «Покупатели» сейчас видят только
   офисные роли (директор, бухгалтер продаж, главный бухгалтер), поэтому для них ничего не меняется. Ограничение проверено
   тестом с ролью салона.
3. **Покупатели — таблица `customers`.** Каждая строка legacy — отдельная запись. 366 названий повторяются (732 строки); их не
   объединяем: по DATA-MAP §3 записи не сливаются только по имени, а объединение — отдельная задача с планом замен, как у статей.
   Тип хранится как в legacy: «Юр. лицо»/«Физ. лицо» из формы, «client»/«company» у старых строк. Пустые строки становятся
   пустыми значениями. Поля `contact` и `turnover` не хранятся: в legacy они пусты/равны 0 во всех строках, а оборот считается
   из заказов. Строка со значением в этих полях остановит импорт.
4. **Юр. лицо по названию.** Legacy (`renderPersons`) считает запись юр. лицом по типу или по форме собственности в названии
   (ТОО, ИП, АО…). Проверку названия legacy пишет через `\b`, а в JS он не видит границу слова рядом с кириллицей. Поэтому
   «ТОО …» с типом «client» показывается как «Физ. лицо», и проверка по названию не срабатывает ни на одной записи. Здесь граница
   слова определяется по Unicode.
   - Вкладка на реальных данных: legacy показывает «Юр. лица 1 / Физ. лица 2», новая версия — «2 / 1».
   - Все покупатели: юр. лицами становятся ещё 29 записей с типом «client».
5. **Состав «Контрагентов» — как в legacy.** Это прямые покупатели офиса: канал «office» или имя в офисном заказе.
   - Одна строка на название — первая в порядке базы.
   - Поиск по названию и телефону; KPI считаются по показанным строкам.
   - Заказов в новой системе ещё нет, но в данных legacy каждый покупатель из офисных заказов уже имеет канал «office». Поэтому
     список тот же: 4 записи, 3 названия.
   - Порядок совпадает с Supabase во всех 5226 позициях: проверено GET-запросом 14.10.2026, сравнение по ICU `en-US`, как в ADR-0005.
6. **Окно «Изменить лицо».**
   - Открытие: в legacy строка таблицы передаёт id строкой, а `findPerson` сравнивает его с числом. Окно правки не открывается
     (TypeError). Здесь окно открывается.
   - Сохранение — по id записи (QA-041). Legacy искал запись по уже новому названию; при совпадении названий изменились бы все
     дубли.
   - Старые типы «client»/«company» форма не предлагает: показывается тип, как его показывает список.
   - Правка меняет только название, тип, ИИН/БИН и телефон, как форма legacy.
   - Действует защита от одновременной правки (`lock_version`) и журнал аудита.
7. **Канал нового покупателя — канал автора** (`getChannelFilter() || 'office'`). Начальник салонов не заводит покупателя без
   выбора салона: legacy записал бы вместо канала служебную метку `__salons__`.
8. **«✓ Сохранено!»** показывается только после ответа сервера (QA-011), окно закрывается через 900 мс, как в legacy.
9. **Перенос данных:** `make legacy-import ENTITY=customers`.
   - Перенесено 5226 строк: офис — 4, салоны — 5222.
   - Импортёр сверяет каждую строку, затем проведена независимая SQL-сверка: 0 расхождений по всем полям, включая время
     создания с микросекундами.

## Не перенесено в этой части

- Вкладки «Дилеры», «Салоны», «Сверки»: сейчас на них сообщение о переносе. Дилеры, салоны и продавцы legacy живут в массивах
  кода, и их правки не сохранялись (QA-042). Их перенос строится на справочнике каналов.
- «Оборот» и «Заказов» считаются из офисных заказов по правилам legacy и появятся с переносом заказов (M09, ERP-029). До этого
  в колонках «—».
- Выбор периода («Текущий год» и др.) в legacy пересчитывает только дилеров и салоны.
- Отчёт «Центры прибыли» (M13, `buildChannelPL`) — после заказов и денег (ERP-062).
