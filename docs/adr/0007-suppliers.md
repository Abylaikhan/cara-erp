# ADR-0007. Поставщики (M06): справочник, карточка, перенос данных, импорт CSV, объединение дублей

Статус: **принято**. Дата: 14.10.2026. Источник legacy: page-suppliers L3238–3342, supplierCardModal L3345–3450,
`loadSuppliersFromDB` L778, `renderSupplierKPIs`/`renderSupplierList`/`renderSupCategories`/`renderSupRating`/`renderSupHistory`/
`openSupplierCard`/`saveSupplierCard`/`deleteSupplier` L18347–18780, `normSupNameMerge`/`findSupplierForName` L17891–17925.

## Решения

1. **Все поля карточки сохраняются.** Адрес, срок поставки, оборот за год и % брака legacy держит только в памяти страницы
   (`saveSupplierCard`, `localExtra`): после перезагрузки они пропадают. Здесь они хранятся в базе. «Оборот за год» —
   ручное поле карточки, как в legacy. Считать ли его по оплатам — вопрос раздела «Деньги».
2. **Статья расхода — одна ссылка на справочник «Статьи расходов».** Хранится статья, а если статья не выбрана —
   категория; legacy хранит два кода.
   - Ссылка зарегистрирована для объединения статей: при объединении в M14 поставщик переходит на новую статью
     (проверено тестом).
   - Если статью удалили в M14, карточка показывает её с пометкой «(удалена)» и при сохранении ссылку не теряет.
3. **Проверка дублей при создании — как в legacy `findSupplierForName`.** Сначала по БИН, затем по нормализованному
   названию, затем по вхождению одного названия в другое.
   - Нормализация повторена вместе с особенностями legacy и сверена с исходной функцией JS на 18 строках. Юрформы не
     удаляются: шаблон с `\b` в JS не срабатывает рядом с кириллицей. Казахские буквы (ә, қ, ң…) превращаются в пробелы.
   - Из-за вхождения система откажет в создании поставщика, чьё название входит в другое (например, «Строй» при
     «Стройматериалы»). Так работает legacy; изменить правило — решение заказчика.
4. **Удаление — деактивация.** Legacy удаляет запись. После переноса оплаты, ЭСФ и закупки будут ссылаться на поставщика,
   поэтому запись сохраняется.
5. **Расчёты — без изменений.** Рейтинг, KPI, вкладки «По категориям» и «Рейтинг» считаются по правилам legacy.
   «История закупок» пуста, как и в legacy: её загрузчик всегда возвращает пустой список (`loadPurchasesFromDB`, L24978).
6. **Права — как в legacy:** все роли со страницей «Поставщики» (директор, кладовщик, закупщик). Собственных проверок в
   функциях legacy нет.
7. **Перенос данных:** `make legacy-import ENTITY=suppliers`, после статей расходов.
   - Перенесено 265 поставщиков: 126 с БИН, 31 со статьёй расхода.
   - Построчная проверка импортёра и SQL-сверка — 0 расхождений.
   - Порядок совпадает с Supabase во всех 265 позициях (проверено GET-запросом).

## Часть 2: импорт CSV и объединение дублей

8. **Импорт CSV — по правилам legacy `importSuppliersCSV`.**
   - Колонки ищутся по заголовку, включая названия из 1С УНФ.
   - Строка сверяется со списком по БИН, затем по нормализованному названию. Известному поставщику дополняются только пустые
     поля; повтор строки в файле пропускается.
   - Тексты подтверждения и итога — как в legacy.
   - Сервер считает план дважды: первый раз для подтверждения (ничего не пишет), второй раз применяет его одной транзакцией.
     Если список за это время изменился, применяется актуальный план.
   - Оборот и срок поставки из файла сохраняются (legacy держал их в памяти страницы). Срок хранится в целых днях,
     с округлением.
   - Файл не в UTF-8 и слишком длинные значения отклоняются до записи: legacy сохранил бы искажённые названия или получил
     бы ошибку базы.
9. **«Объединить».**
   - Группы и основная запись по умолчанию считаются в браузере функциями legacy: одинаковый БИН, совпадающее или похожее
     название (сходство ≥ 80 %). «Это разные поставщики» действует до перезагрузки, как в legacy.
   - Сервер объединяет выбранное: пустые поля основной записи заполняются из остальных, их названия добавляются в
     комментарий, оборот суммируется (legacy суммировал его только на экране).
   - Остальные записи не удаляются, а деактивируются со ссылкой на основную.
   - Ссылки других модулей переносятся по реестру `supplier_references`. Сейчас он пуст: деньги, ЭСФ и закупки добавят свои
     ссылки при переносе.
   - Счётчики ссылок до и после и заполненные поля сохраняются в журнале объединений (ТЗ M06, AC-58).
   - На реальных данных legacy и новая версия показывают одни и те же 4 группы (visual-compare 0,02 %).
10. **Шаблон CSV не перенесён.** Функция `downloadSupplierTemplate` в legacy есть, но ни одна кнопка её не вызывает.

## Не перенесено в этой части

- Эти функции работают с денежными операциями и ЭСФ и появятся после разделов «Деньги» (M12) и «Входящие ЭСФ» (M05):
  - «Импорт из ЭСФ»;
  - «Осиротевшие в операциях»;
  - «Разночтения написаний»;
  - «Сократить юрформы»;
  - список ЭСФ в карточке.
- Переименование поставщика в legacy предлагает переписать его название в операциях (`renameSupplierInMoneyTx`). В новой
  системе операции будут ссылаться на поставщика по id, поэтому переписывать их не придётся.
