# ADR-0024. Репетиция переноса и контрольные итоги

Статус: **принято**. Дата: 16.10.2026. Требования: ERP-069 (ТЗ MIG: «Сверены все модули/периоды; каждое расхождение
объяснено»).

## Решения

1. **Репетиция** (`make migration-rehearsal`, `scripts/migration-rehearsal.sh`) идёт на временной пустой БД на том же сервере
   PostgreSQL. dev-БД только читается: из неё копируется схема `legacy` с загруженным снимком (только чтение Supabase,
   ADR-0004).
   - Порядок шагов:
     1. все миграции (каналы продаж и склады заводятся миграциями; демо-сидер не запускается);
     2. все `legacy:import` в порядке зависимостей с замером времени;
     3. `ANALYZE`: после массовой загрузки у планировщика нет статистики (ADR-0025, п. 1.3);
     4. `legacy:control-totals`;
     5. повтор всех импортов.
   - Повтор не должен менять бизнес-таблицы: отпечаток БД (ADR-0012) снимается до и после повтора. Меняться могут только
     журнал аудита и время импорта в `legacy_id_map`.
   - Временная БД удаляется всегда; `KEEP=1` оставляет её для разбора.
   - Отчёт, журнал и детали с суммами пишутся в `.local-audit/rehearsal/<время UTC>/` (вне Git, права только у владельца).
2. **Контрольные итоги** (`php artisan legacy:control-totals [--snapshot=] [--out=]`).
   - По каждому перенесённому модулю итоги считаются дважды: по JSON снимка legacy и по таблицам приложения. Сравнение
     точное.
   - Что считается:
     - число записей;
     - суммы денег и количеств;
     - признаки (активна, перенесена, завершено).
   - В каких разрезах:
     - для документов — по месяцу бизнес-даты (для моментов времени — по Asia/Almaty) и направлению;
     - для справочников — по своему разрезу: канал/тип, статус, категория, склад.
   - Сторона legacy — отдельный SQL, независимый от импортёров. Из правил импортёров он повторяет только задокументированные
     преобразования:
     - значения по умолчанию;
     - округление ЭСФ и бюджета лида до копеек;
     - округление цены материала по правилу JS;
     - слияние одинаковых синонимов.
   - Команда сверяет и таблицы снимка, у которых нет импортёра. Такая таблица допустима, если в ней нет записей или для неё
     записана причина (модуль ещё не перенесён). Иначе — «НЕ ОБЪЯСНЕНО» и ошибка.
   - В консоль выводятся только количества и статусы. Суммы попадают только в файл `--out`.
   - Команда рассчитана на БД, заполненную импортом. Записи, заведённые в самом приложении, она покажет как расхождения.
3. **Исправлено по итогам репетиции** (`IncomingInvoiceImporter`):
   - повторный импорт удалял и заново вставлял все строки ЭСФ и связи с оплатами: данные те же, но новые id и рост
     последовательностей. Теперь набор строк или связей счёта переписывается только когда он отличается от legacy;
     в статистике импорта — `lines_rewritten` и `links_rewritten`;
   - время связи с оплатой теряло микросекунды: построитель запросов форматирует Carbon как `Y-m-d H:i:s`. Теперь время
     передаётся текстом с микросекундами, как в `MoneyImporter`. Уже загруженные связи dev-БД исправлены повторным импортом.

## Часть 2. Пробный прогон, журнал ошибок, отчёт по ссылкам (ТЗ MIG-02, AC-75, 16.10.2026)

1. **Пробный прогон** — `legacy:import <таблица|all> --dry-run`.
   - Тот же импорт, что и настоящий: проверка всего набора, запись, построчная сверка. Всё выполняется во внешней
     транзакции, которая откатывается.
   - Показывает, что будет создано, изменено и удалено, и ничего не оставляет — даже журнала аудита и карты legacy ID.
     Пропускаются только номера последовательностей.
   - `all` выполняет все таблицы в порядке зависимостей. В пробном прогоне они идут в одной транзакции, поэтому
     зависимые таблицы видят ещё не записанные данные предыдущих.
2. **Журнал ошибок** — `--errors=<файл>`.
   - Отклонённый набор по-прежнему ничего не записывает. В консоль выводятся первые 10 проблем, в файл — все (0600,
     только в `.local-audit`).
   - Все импортёры отклоняют набор одним исключением `LegacyRejected` с полным списком проблем.
3. **Отчёт по ссылкам** — `legacy:references [--out=<файл>]`, только чтение снимка.
   - По каждой ссылке перенесённых таблиц: сколько найдено ровно одно, ни одного (не найдено) или несколько
     (неоднозначно), и правило импорта:
     - набор отклоняется;
     - переносится без связи, значение остаётся текстом;
     - связь только при единственном совпадении — не выбирается произвольно (ТЗ MIG-02).
   - Отдельно — повторяющиеся названия и номера.
   - Ключи записей попадают только в `--out` (0600). Если импорт отклонит снимок, отчёт заранее называет причину.
4. **Репетиция**:
   - отчёт по ссылкам;
   - `legacy:import all --dry-run` — отпечаток всех таблиц до и после должен совпасть;
   - импорт с журналом ошибок по каждой таблице.

   Снимок 20261015T172631Z: пробный прогон около 14 с и ничего не записал; затем PASS, как в части 1.

## Повтор на свежем снимке 20261019T075008Z (19.10.2026)

Копия legacy обновлена только чтением: 44 таблицы, 57 994 строки, 244 GET-запроса, других методов 0. С 15.10 изменилось
в legacy:
- выписки банка — +410;
- денежные операции — +142: в legacy и удаляли операции (новая сверка переводов на кассу ЗП);
- начисления ЗП — +7;
- статьи расходов — +1;
- связи ЭСФ с оплатами — −1.

**Репетиция — PASS.** Итоги совпали по 22 модулям, 49 058 записей. Первый прогон — 18 с, повтор — 19 с и ничего не
изменил. Новых нераспознанных ссылок нет: по-прежнему 286 реализаций, 93 операции и 8 оплат с номерами
несуществующих заказов (вопрос заказчику).

**Перенос в dev-БД** (`legacy:import all`): все 17 импортов сверены построчно.
- Деньги: 309 новых операций, 153 изменённых, 167 удалённых (удалены в legacy; значения сохранены в журнале аудита).
- Выписки: 410 новых. Статьи расходов: 1 новая.
- Остальное без изменений.

`legacy:control-totals` — 22 из 22 «совпадает».

## Не сделано

- Перенос в production (ТЗ MIG): `legacy:import` в окружении production запрещён. Нужны:
  - окно переноса;
  - заморозка legacy на время снимка;
  - решение по таблицам выше.
