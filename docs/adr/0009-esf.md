# ADR-0009. Входящие ЭСФ (M05), часть 1: список, просмотр, импорт XML

Статус: **принято**. Дата: 14.10.2026. Источник legacy: page-esf L3056–3238, esfDetailModal L3179, esfXmlImportModal,
`initEsfPage`/`renderEsfList`/`setEsfType`/`openEsfDetail` L11926–12560, `parseEsfXmlText` и помощники L11979–12105,
`handleEsfXmlFiles`/`renderEsfXmlImportPreview`/`confirmEsfXmlImport` L12107–12220.

## Решения

1. **Разбор XML — на сервере, по правилам legacy.**
   - Каждый `invoiceInfo` — отдельная ЭСФ: регистрационный номер и статус снаружи, сама ЭСФ — вложенный XML в CDATA
     (`invoiceBody`).
   - Дата — дата оборота, если она есть, иначе дата документа.
   - Поставщик — `sellers/seller`, не грузоотправитель; длинная юрформа сокращается («ТОО …»).
   - Теги ищутся как в браузере: сначала точное имя, потом локальное имя без учёта регистра.
   - Числа остаются точными десятичными строками, без float.
   - Разбор сверен с исходной функцией JS на образце и семи пограничных случаях: повреждённый XML, нет `invoiceInfo`,
     пустое тело, повреждённое вложенное XML, другой регистр, префикс, нет строк. Результаты совпали.
   - Внешние сущности и сеть при разборе отключены. Ограничения: 50 файлов по 5 МБ.
2. **Импорт — предпросмотр, затем выбранное.**
   - Разобранные ЭСФ ждут выбора на сервере час; подтверждение импортирует ровно то, что было показано.
   - Дубли отмечаются как в legacy: совпал регистрационный номер или совпали дата, номер, поставщик и сумма (±1 ₸).
     Дубли по умолчанию не отмечены.
   - Каждая ЭСФ со строками сохраняется одной транзакцией. Регистрационный номер уникален: повторная загрузка той же
     ЭСФ отклоняется с объяснением (в legacy — «ошибок: N (см. консоль)»).
   - Поставщик ищется по правилам `findSupplierForName`. Если не найден — создаётся; если найден без БИН — получает БИН.
3. **Итоги ЭСФ хранятся до копейки.** В legacy итоги — дробные суммы строк в JS (артефакты до 14 знаков). Перенесённые
   итоги совпадают с суммой строк у всех 1386 ЭСФ.
4. **Порядок.**
   - Строки ЭСФ — в физическом порядке таблицы legacy: так их показывает legacy, и это порядок вставки из XML. Колонки
     для сортировки в таблице нет, поэтому порядок прочитан отдельно, только GET-запросами
     (`legacy:natural-order incoming_invoice_items`, два одинаковых чтения подряд).
   - Список — по дате, новые выше. Внутри одной даты порядок в legacy не определён: он зависит от сортировки в
     PostgreSQL и не совпадает ни с одним полем, что проверено. Здесь внутри даты — по времени загрузки, новые выше.
5. **Сверка показывается, но не меняется.** Связи ЭСФ с платежами и авансовыми отчётами (`esf_payment_links`, 1506)
   перенесены: колонка «Сверка» и сводка считаются по ним, как в legacy. Платёж указан legacy-идентификатором до
   переноса «Денег». Вкладка «Сверка с оплатами» (ручная и автоматическая привязка) — ERP-048 после решения D-10.
6. **Сопоставление строки с материалом склада работает.** В legacy оно не срабатывает никогда: функция читает
   `window.warehouseData`, а переменная объявлена через `let`. Здесь строка сопоставляется по названию или алиасу по
   правилам legacy, и в окне ЭСФ видно «✅ материал».
7. **Тип ЭСФ** (общее/услуги/товары) меняется в списке и сохраняется с записью в журнал.
8. **Права — как в legacy:** страница «Входящие ЭСФ» есть только у директора.
9. **Перенос данных:** `make legacy-copy` (включая физический порядок строк), затем `make legacy-import ENTITY=incoming_invoices`.
   - 1386 ЭСФ, 3471 строка, 1506 связей.
   - 1380 ЭСФ связаны с поставщиком по однозначному БИН.
   - SQL-сверка всех полей, строк и связей — 0 расхождений.

## Не перенесено в этой части

- **Сверка с оплатами, «Создать расход»** — после раздела «Деньги» (ERP-048, D-10).
- **«Принять» строку на склад** — после складских документов (D-04/D-05): в legacy это меняло остаток без документа.
- **«Товары в Excel»** — вместе с остальными выгрузками (ERP-067): для `.xlsx` нужна библиотека, а новые зависимости
  ставятся отдельной задачей.
