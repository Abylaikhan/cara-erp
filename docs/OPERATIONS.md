# PromTech ERP — эксплуатация

Для того, кто запускает, обновляет и восстанавливает систему. Все команды выполняются из папки `application/`.
Нужны только Docker с Compose v2, Make, Git и `python3` ≥ 3.9 на хосте. PHP, Composer, Node и PostgreSQL ставить не
нужно.

Сейчас это рабочее окружение разработки и проверки. Production-развёртывание — отдельный этап после решения D-01
(где будет база, `docs/decisions-request.md`); раздел 8 — что для него уже готово.

## 1. Первый запуск

```sh
git clone https://github.com/Abylaikhan/cara-erp.git && cd cara-erp/application
make setup     # .env из .env.example с новыми паролями, APP_KEY, зависимости из lock-файлов, сборка, миграции, синтетические пользователи, старт
make doctor    # версии, сервисы, порты, подключение к PostgreSQL, HTTP — без вывода секретов
```

- Приложение: http://localhost:8080 (порт — `APP_PORT` в `.env`). Все порты открыты только на 127.0.0.1.
- Вход: логин — ключ роли (`director`, `accountant`, `manager`, `salon_armada`, `dealer_astana`, …), пароль —
  `DEV_ADMIN_PASSWORD` из `.env`. Это синтетические пользователи разработки.
- `make setup` можно повторять: `.env`, `APP_KEY` и данные не перезаписываются.

## 2. Каждый день

| Команда | Что делает |
|---|---|
| `make up` / `make down` / `make restart` | запустить, остановить, перезапустить; тома с данными сохраняются |
| `make ps`, `make logs` (`S=app` — один сервис) | состояние и журналы сервисов |
| `make shell`, `make psql` | консоль контейнера приложения, psql к dev-БД |
| `make audit-daily` | ежедневный аудит: legacy и целевой код, отчёт в `docs/daily/`; на GitHub — ежедневно (Actions «Daily audit», расписание 07:17, GitHub запускает около 12:00; отчёт — артефакт) |

- Журнал приложения — `storage/logs/laravel.log`.
- Очередей и задач по расписанию приложение пока не использует: все операции выполняются сразу, отдельный обработчик
  не нужен.

## 3. Обновление

1. `make db-backup` — копия до обновления. Откат идёт через неё (раздел 6).
2. `git pull`.
3. `make setup` — зависимости из lock-файлов, сборка, новые миграции. Данные и `.env` сохраняются.
4. `make check` — стиль, типы, сборка, все тесты на изолированной тестовой БД.
5. `make doctor`, затем вход и просмотр основных страниц.

Зависимости ставятся только из lock-файлов (`composer.lock`, `package-lock.json`); `composer update` и `npm update` без
отдельной задачи не выполняются.

## 4. Резервная копия

```sh
make db-backup                                   # → .local-audit/backups/<время UTC>-<коммит>/
make db-restore-check                            # проверка последней копии; другой — BACKUP=<каталог>
```

**Что в копии:**
- дамп БД;
- загруженные файлы (`storage/app`: файлы проектов CRM) со списком SHA-256;
- манифест: коммит, версия PostgreSQL, отпечаток каждой таблицы;
- ответы приложения каждому пользователю — только контрольные суммы.

Каталог доступен только владельцу (0700/0600): в нём реальные данные. Копия делается согласованно: если во время
копирования что-то изменилось, она снимается заново.

**Что делает проверка.** Восстанавливает копию отдельно от рабочей БД, сверяет:
- схему, все таблицы и последовательности;
- каждый файл;
- ссылки `project_files`.

Затем запускает приложение на копии: каждый пользователь должен увидеть то же, что при копировании. Подробно —
`docs/adr/0012-db-backup.md`.

**Чего нет.** Хранения копий вне этой машины и расписания — они на стороне инфраструктуры заказчика (D-01). Пока
копировать каталог `.local-audit/backups/<…>` целиком в защищённое хранилище.

## 5. Восстановление

Проверено буквально на одноразовой базе. Рабочая БД не перезаписывается, пока новая не проверена.

```sh
B=.local-audit/backups/<каталог>
make db-restore-check BACKUP=$B                                                   # 1. копия цела и приложение на ней отвечает
git checkout <app.commit из $B/manifest.json>                                     # 2. код той же версии
docker compose exec -T db sh -c 'createdb -U "$POSTGRES_USER" promtech_restored'  # 3. новая пустая база
docker compose exec -T db sh -c 'pg_restore -U "$POSTGRES_USER" -d promtech_restored --no-owner --no-privileges --exit-on-error' < $B/db.dump
docker compose exec -T db sh -c 'psql -X -q -U "$POSTGRES_USER" -d promtech_restored -c ANALYZE'
mkdir -m 700 storage-restored                                                     # 4. файлы с проверкой каждого
python3 scripts/backup_files.py verify $B/files.tar $B/files.tsv storage-restored
mv storage/app storage/app.before && mv storage-restored storage/app              # 5. переключение
#    в .env: DB_DATABASE=promtech_restored
make restart && make doctor                                                       # 6. проверка и вход
```

- `.env` в копии нет: пароли БД и `APP_KEY` хранятся отдельно.
- Шифрованных данных в БД нет. Новый `APP_KEY` только завершит сессии; пароли пользователей хранятся в БД как хеши.
- Если код новее копии, после шага 5 выполнить `docker compose run --rm app php artisan migrate --force`.
- Старая БД и `storage/app.before` остаются до подтверждения.

## 6. Откат обновления

Миграции имеют обратный ход, но надёжнее восстановить копию, сделанную перед обновлением (раздел 3, шаг 1):
1. `git checkout <предыдущий коммит>`;
2. восстановление этой копии по разделу 5.

Пока копия не восстановлена, данные, внесённые после обновления, не теряются: они остаются в текущей БД.

## 7. Данные legacy и перенос

- **Копия Supabase** — `make legacy-copy`, только GET. Снимок хранится локально в `.local-audit/supabase/` (вне Git) и
  загружается в схему `legacy`. Пароли и PIN не копируются (ADR-0004).
- **Отчёт по ссылкам** — `docker compose run --rm app php artisan legacy:references`: что не найдено или неоднозначно и
  как это переносится.
- **Репетиция** — `make migration-rehearsal`: временная БД, пробный прогон, все импорты, `ANALYZE`, контрольные итоги
  по модулям и периодам, повтор без изменений (ADR-0024).
- **Перенос в рабочую систему** — по плану раздела 11, после решения D-01. Supabase не меняется, поэтому откат —
  вернуть пользователей в legacy. `legacy:import` отказывается работать при `APP_ENV=production`: переключение —
  отдельно разрешённый этап (ERP-078).
- **Повторный перенос после работы в новой системе.** Некоторые импорты переписывают данные, которые новая система уже
  умеет менять. Поэтому они останавливаются с объяснением и ничего не меняют:
  - `legacy:import incoming_invoices` — если связи ЭСФ с оплатами уже сохраняли или удаляли здесь (ADR-0048);
  - `legacy:import warehouse` — если складские документы уже двигали остатки (ADR-0049).

  Счета «Денег», изменённые здесь, перенос сохраняет как есть; удалённые не возвращает (ADR-0047).

## 8. Production (готовность)

**Уже готово:**
- сборка `npm run build`;
- миграции без демо-данных: синтетический сид отказывается работать в production;
- `legacy:import` в production заблокирован;
- резервная копия и проверка восстановления;
- репетиция переноса;
- проверки надёжности (ADR-0025);
- `make prod-check` — приложение в режиме production на временной БД (ADR-0031, в аудите — `TGT-PROD`):
  - PHP пишет ошибки в журнал, а не на страницу;
  - кэши собираются;
  - страницы ошибок без подробностей;
  - собранные ресурсы без сервера разработки;
  - в сборке нет секретов.

**Нужно решить и настроить на этапе развёртывания:**
- где PostgreSQL 17 (D-01);
- домен и HTTPS;
- `APP_ENV=production`, `APP_DEBUG=false`, `LOG_LEVEL` не ниже `warning`;
- `php artisan config:cache route:cache view:cache` после каждого обновления;
- расписание копий и их хранение вне сервера;
- реальные пользователи и новые пароли (D-13).

Порядок разворачивания и первой проверки будет записан здесь после решения D-01.

## 9. Проверки

| Команда | Что проверяет |
|---|---|
| `make check` | стиль, типы, сборка, все тесты на изолированной тестовой БД (выполняется и в CI на каждый push) |
| `make harness-selftest` | самопроверки аудита, в том числе H-24 (копия → восстановление) |
| `make visual-compare` | скриншоты legacy и новой версии, % отличий при 1440×900 (Playwright и Chrome на хосте; другой размер — `VIEWPORT=1920x1080`) |
| `make test-visual` | то же на всех размерах спецификации: 1440×900, 1920×1080, 900×900, 899×900, 390×844 (около 40 минут) |
| `make visual-empty` | то же на пустой базе (только пользователи), через `make e2e`: пустые состояния всех перенесённых страниц |
| `make visual-filters` | то же плюс каждый фильтр, сортировка и детализация перенесённых страниц на обеих сторонах (около 35 минут) |
| `make reliability-check` | ответ 500, обрыв связи, истёкшая сессия, двойное нажатие — в браузере; изменяющие запросы перехватываются |
| `make e2e` (= `make test-e2e`) | сценарии приёмки в браузере на временной БД и отдельном экземпляре (CRM, справочники, окна, загрузка и её ошибка); dev-БД проверяется на неизменность |
| `make audit-replay RUN_ID=…` | повтор записанного запуска аудита на его refs без публикации и сравнение с записью |
| `make registry` | статус каждой страницы, окна, элемента и функции принятого legacy (реализовано, не начато, ждёт решения…), `docs/coverage/registry.md` |
| `make migration-rehearsal` | перенос legacy на временной БД с контрольными итогами |
| `make prod-check` | режим production на временной БД рядом с dev-окружением: настройки PHP, отказы, кэши, страницы ошибок, ресурсы, секреты в сборке |
| `make perf` | время ответа и размер каждой перенесённой страницы и вкладки (только чтение; ADR-0032) |

Браузерные сценарии, которые создают или меняют записи, запускаются только через `make e2e`. Не на dev-приложении
(там копия реальных данных) и не через `php artisan serve` (ADR-0026).

## 10. Секреты

| Что | Где | Замечание |
|---|---|---|
| пароли БД, `DEV_ADMIN_PASSWORD` | `.env` (вне Git) | создаются `make setup`; в `.env.example` — заглушки `__GENERATE__` |
| `APP_KEY` | `.env` | данные им не шифруются; смена завершает сессии |
| `LEGACY_SUPABASE_URL`, `LEGACY_SUPABASE_ANON_KEY` | `.env` | только чтение legacy |
| ключи Google Sheets | `~/.config/promtech/` на машине исполнителя | вне репозитория |

Секреты не выводятся в отчёты аудита: проверка `HAR-SECRETS` ищет их в отчётах и журналах. Репозиторий публичный,
поэтому в нём нет ни реальных данных, ни секретов.

## 11. Переключение с legacy и откат (черновик)

Черновик плана для ERP-078. Уточняется после решения D-01 (где работает система) и D-13 (пользователи). Каждый шаг
выполняется только с разрешения заказчика.

**До дня переключения:**
1. Заказчик принял разделы, которые переносятся. Открытые решения и что остаётся в legacy — `docs/decisions-request.md`.
2. Рабочий сервер развёрнут по разделу 8, `make prod-check` проходит.
3. Учётные записи перенесены (`legacy:import app_users`, ADR-0045) и получили новые пароли:
   `php artisan users:issue-passwords --out=<файл>` — файл читает только владелец; раздать пароли и удалить файл. Старые
   пароли и PIN известны посторонним (вопрос № 73).
4. Владелец закрыл доступ к репозиторию legacy `Cara-ERP/promtech-erp` (решение 23.10.2026, вопрос № 73). Если сайт
   legacy публикуется через GitHub Pages, сначала проверить, что он продолжит работать до дня переключения.
5. Не раньше чем за неделю — репетиция на свежем снимке: `make legacy-copy`, затем `make migration-rehearsal`.
   Все модули сходятся, повтор ничего не меняет. По времени прогона планируется окно переключения: на снимке 22.10
   импорт занял 23 с.
6. Пользователей предупредили о дне и часе. В это окно legacy не используется.

**День переключения:**

| Шаг | Что делаем | Проверка |
|---|---|---|
| 1 | Владелец legacy закрывает в нём запись: отключает сайт или его ключ. Мы в Supabase не пишем | новые записи в legacy не появляются |
| 2 | Итоговый снимок: `make legacy-copy` (только GET) | у каждой таблицы SHA-256 в `manifest.json`; загрузка сверяет число строк и содержимое |
| 3 | Репетиция на этом снимке: `make migration-rehearsal` | PASS по всем модулям |
| 4 | Копия рабочей БД до импорта: `make db-backup` | `make db-restore-check` проходит |
| 5 | Импорт в рабочую БД по порядку `legacy:import all` и контрольные итоги `legacy:control-totals`. Как снимается запрет импорта в production — решается в ERP-078 | все модули «совпадает» |
| 6 | Проверка под каждой ролью: вход, главные страницы, свой канал. Время ответа — `make perf` | ответы без ошибок, в пределах ADR-0032 |
| 7 | Открытие для пользователей | — |

**Откат.** Если до конца первого рабочего дня итоги не сходятся или найден дефект, который мешает работать:
1. `php artisan down` — новая система закрыта для пользователей.
2. Владелец legacy снова открывает запись. Данные Supabase мы не меняли, legacy продолжает с того же места.
3. Записи, сделанные в новой системе после открытия, переносятся в legacy вручную. Их список — по журналу аудита
   (`audit_events`: кто, когда, что). Поэтому окно между открытием и решением об откате должно быть коротким.
4. Причина записывается в трекер. Следующая попытка — после исправления и новой репетиции.

**Первый день после открытия:**
- журнал `storage/logs/laravel.log` — без ошибок;
- копия БД сделана по расписанию и проверена;
- legacy остаётся закрытым для записи и доступен только для чтения на время, которое назовёт заказчик.
