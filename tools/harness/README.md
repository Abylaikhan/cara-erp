# Harness ежедневного аудита

Детерминированный контур проверок по ТЗ (`HARNESS-DEVELOPMENT-SPEC.md` §6–§10, §13). Код делает проверки;
модель Claude только дополняет разбор и не меняет их результаты.

```sh
make audit-daily                      # полный аудит: legacy + целевой код, MD/JSON-отчёт, журнал
make audit-daily TARGET_REF=<ref>     # аудит конкретного коммита/ветки целевого кода
make harness-selftest                 # сценарии H-04…H-21 на локальных фикстурах, H-24 на временной БД сервиса db
python3 tools/harness/run.py status   # указатели состояния
```

Требуется Docker и `python3` ≥ 3.9 (на macOS идёт вместе с git, на CI-раннерах установлен). Внешних Python-пакетов нет.

## Стадии одного запуска

1. **Lock и попытка.** `fcntl`-lock в `.local-audit/run.lock`; второй запуск получает `ALREADY_RUNNING` (exit 75) и ничего не меняет.
   Попытка записывается в `docs/audit/state.json` до сетевых действий; незавершённая попытка видна следующему запуску.
2. **Источник (legacy).** `git ls-remote` один раз фиксирует HEAD; дальше всё идёт по SHA (`git fetch` по SHA, без checkout).
   Blob берётся только по точному пути `index.html`, проверяются git-хеш, размер и SHA-256; коллизии регистра
   (`Index.html`) фиксируются. Принятый эталон из `config.json` сверяется по SHA-256. Диапазон коммитов — от прошлого
   отчёта, а не «за сутки»; если прежний ref не предок нового — `HISTORY_DIVERGED`.
3. **Inventory** (`node/legacy_inventory.mjs`, parse5 + acorn) — в контейнере `--network none --read-only`, без Docker socket,
   анализируемый код не исполняется. Страницы, модальные окна, элементы управления, функции (AST, хеш токенов),
   вызовы таблиц БД, хранилище, внешние ресурсы, синтаксис скриптов. Встроенные секреты legacy попадают только в
   локальный список редактирования.
4. **Diff и влияние** (`compare.py`): добавленные/удалённые/изменённые функции, страницы, таблицы; через граф вызовов
   от обработчиков кнопок — затронутые страницы и модули M01–M23; связь с `docs/coverage/requirements.csv`, иначе `UNMAPPED_CHANGE`.
5. **Целевой код** (`target.py`): чистый `git worktree` зафиксированного коммита, отдельный Compose-проект `promtech-audit`
   (свой `.env`, свои тома, случайные порты). Шаги — те же, что у `make check`: `scripts/check.sh deps pint types build tests migrate dbcheck http`;
   после миграций `backup` (`TGT-BACKUP`): копия синтетической БД аудита и файлов восстанавливается во временный контейнер того же
   образа. Схема, строки и контрольные суммы каждой таблицы и последовательности, файлы по SHA-256 и ссылки `project_files`
   должны совпасть. Приложение на копии отвечает каждому пользователю на каждой странице так же, как при копии
   (`app:view-digest`; H-24, ADR-0012, часть 2).
6. **Google Sheets** (`tasks.py`): чтение трекера по API-ключу; запись требует service account — до этого `BLOCKED`.
7. **Самоконтроль:** `HAR-COVERAGE` (исчезнувшие проверки/тесты → FAIL и review), `HAR-JOURNAL` (журнал не потерял записи),
   `HAR-SECRETS` (секреты и маркеры отсутствуют в MD, JSON и логах).
8. **Claude** (`ai_review.py` → `node/ai_review.mjs`, официальный SDK): по умолчанию выключен (`config.json → ai_review.enabled`).
   Получает только уже собранные данные без секретов, отвечает по JSON-схеме, проверяет бюджет до вызова.
   Утверждения без ссылки на доказательство помечаются как гипотезы; рекомендации закрыть находку не применяются.
9. **Публикация:** `docs/daily/<дата>/<run_id>.md|json`, запись в `docs/DAILY-CHANGELOG.md`, реестр `docs/audit/findings.json`,
   затем указатели `docs/audit/state.json`. Каждый файл пишется атомарно; при ошибке публикации остаётся локальный
   отчёт в `.local-audit/runs/<run_id>/`, и запуск не считается успешным.

## Расписание (GitHub Actions)

`.github/workflows/daily-audit.yml` запускает тот же `make audit-daily`:
- ежедневно в 07:17 по Алматы (`config.json → schedule.cron_utc`, GitHub может задержать запуск — пропуски покрывает
  следующий по сохранённому ref);
- вручную (`workflow_dispatch`);
- один раз при изменении самого файла: настоящий прогон подтверждает задание и права.

Порядок работы:
- Одна группа параллельности: второй запуск ждёт первый.
- Задание аудита имеет токен только на чтение. Отчёты, журнал, state и журналы прогона сохраняются артефактом при любом
  исходе (90 дней). Трекер и модель там недоступны — `BLOCKED`.
- Публикация в Git — отдельным заданием с правом записи. Включается переменной репозитория `AUDIT_REPORTS_BRANCH`
  (например `audit-reports`): в эту ветку копируются только `docs/daily/`, журнал и state, любой другой путь — отказ.
  Без переменной публикации нет, отчёт — артефакт (спецификация: `BLOCKED`).
- Аудит не пишет в `main`, ничего не сливает и не развёртывает.

## Статусы и коды выхода

Каждая проверка: `PASS`, `FAIL`, `BLOCKED`, `NOT_RUN`, `NOT_APPLICABLE`. Отдельно: `execution_status`
(`COMPLETE`/`PARTIAL`/`BLOCKED`), `product_status` (`PASS`/`FAIL`/`UNKNOWN`, только целевой код), `source_status`.

| Exit | Значение |
|---|---|
| 0 | все обязательные проверки PASS, отчёт опубликован |
| 1 | провал обязательной проверки |
| 2 | обязательный набор неполный (BLOCKED/NOT_RUN) или публикация не удалась |
| 3 | ошибка самого harness |
| 75 | уже идёт другой аудит |

Находка получает стабильный ID (`AF-…`) и закрывается только когда её проверка прошла на **новом** ref; прохождение на
том же ref — `NEEDS_REVIEW`, исчезнувший тест — `NEEDS_REVIEW`.

## Конфигурация и секреты

`config.json` — версионируемая конфигурация без секретов (репозитории, точный путь, принятый эталон, шаги, лимиты).
Локальное дополнение вне Git — `~/.config/promtech/harness.local.json` (ID таблицы), ключи — в `~/.config/promtech/`.
`accepted_ref` меняется только отдельным решением, не ежедневным запуском.
